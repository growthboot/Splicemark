Splicemark / Guide

Authorship-aware editing for coding agents sharing one working tree.

Splicemark gives each agent a task identity, records exact mutations when they happen, keeps routine review local to that task, and surfaces other agents only when their work intersects the same code.

Start here
splicemark start "fix queue recovery"
splicemark edit sm-… src/queue.js --lines 42:42 \
  --expect-start "return retry(job);" \
  --expect-end "return retry(job);"

There is no daemon, account, branch orchestration, or separate merge model. Git remains the aggregate source of truth. Splicemark owns only the coordination around uncommitted edits.

00

The model

Multiple agents work in the same physical tree. Splicemark records who changed what at mutation time instead of trying to infer authorship later from an aggregate diff.

Agent A session sm-a
→
Splicemark attribution + local coordination
→
shared working tree ordinary files
→
Git aggregate history
Agent B session sm-b
Mutation-time authorship

Ownership is known because Splicemark performs the write.

Local awareness

Unrelated agents stay invisible. Overlap is what creates coordination context.

Git authority

Once HEAD absorbs a mutation, active Splicemark attribution can retire.

01

Precise edits

A single edit targets an inclusive line or character range and carries expected boundaries. If concurrent work shifts both boundaries by the same amount and the target remains unique, Splicemark relocates it. Ambiguity is refused.

splicemark edit SESSION FILE --lines START:END --expect-start TEXT --expect-end TEXT
Invariant A stale coordinate is acceptable. An ambiguous target is not.
02

Batch writes

When an agent has already validated several non-overlapping ranges against one snapshot, they can be submitted together. Splicemark sorts them bottom-to-top and writes the resulting file once.

splicemark batch SESSION FILE --lines < splices.json
Why bottom-to-top? An earlier write cannot move a lower range before that lower range has been applied.
03

Peer awareness

Splicemark is not an agent activity feed. A peer edit is surfaced when another active session owns work in the region the current edit is entering. Everything else remains outside the task context.

Scope same file + overlapping active line region + compatible HEAD
04

Code-bound notes

Notes exist for exceptional coordination that cannot be expressed by authorship alone. They are attached to code, not sent to an agent, and are shown only when another active session enters the noted region.

splicemark note SESSION FILE --lines START:END --message TEXT
Lifetime A note belongs to the HEAD on which it was created and stops participating as soon as HEAD changes.
05

Git reconciliation

Splicemark does not compete with Git. When HEAD changes, active authorship is compared with the committed and working diffs and classified as active, retired, or stale.

active the authored mutation is still in the working tree and not in the new commit
retired the mutation was absorbed by Git
stale Splicemark can no longer map ownership unambiguously
06

CLI reference

The command surface is intentionally small. A session starts with a short task description and ends when that task is finished.

start "description" create an active task identity
edit SESSION FILE … perform one validated attributed mutation
batch SESSION FILE … apply prevalidated non-overlapping splices
note SESSION FILE … attach exceptional coordination to code
diff SESSION review active changes attributed to one task
finish SESSION mark the task inactive
clean remove obsolete coordination state

Install from source

git clone https://github.com/growthboot/Splicemark.git
cd Splicemark
npm link

Minimal agent instruction

Start a Splicemark session for the task and retain the returned session ID. Use Splicemark for writes. Use edit for a single validated range or batch after validating all non-overlapping ranges against one snapshot. Use diff SESSION for task-local review and finish SESSION when done.
07

Non-goals

Splicemark is deliberately narrow. These are not missing features; they are boundaries around the problem it is trying to solve.

  • no branches or per-agent worktrees
  • no alternative staging model
  • no merge workflow
  • no agent chat or global activity feed
  • no permanent annotations in source files
  • no replacement for normal Git review and history
